# Code documentation standard

Normative for every source file: Python, TypeScript, SQL, YAML, TOML, shell
and configuration. Goal: explain public interfaces and non-obvious decisions
without repeating the code or embedding project-management history.

`python3 scripts/check_harness.py` enforces the prohibitions below on code
comments; Ruff's `D` rules (Google convention) enforce Python docstrings once
backlog task F01 configures them.

## Python docstrings

Google style, PEP 257 baseline, English only.

- Triple double quotes; an imperative one-sentence summary ending in a period.
- A blank line between the summary and any longer description.
- Document every public module, class, function and method. Private helpers
  get a one-line docstring only when the name is not enough.
- Use `Args:`, `Returns:`, `Yields:` and `Raises:` when they apply. Type hints
  carry the types; the docstring describes meaning, units and constraints.
- Module docstrings: one summary line plus at most a short context paragraph
  (six lines in total).
- Class docstrings state what an instance represents and its invariants; list
  `Attributes:` for data classes and models.

```python
"""Deterministic risk gate for virtual order intents.

Approves, reduces or rejects intents against a versioned policy. It never
calls a model and never changes balances.
"""


def evaluate_intent(intent: OrderIntent, context: RiskContext) -> RiskVerdict:
    """Decide whether an order intent may proceed.

    Checks run in policy order; the first hard violation rejects the intent.

    Args:
        intent: Proposed virtual order, already sized in instrument lots.
        context: Point-in-time portfolio, quotes and policy version.

    Returns:
        Approval, reduction or rejection with machine-readable reason codes.

    Raises:
        StaleQuoteError: If the latest quote is older than the policy limit.
    """
```

```python
@dataclass(frozen=True)
class Fill:
    """Modeled execution of a virtual order against an observed quote.

    A fill is never a claim of exchange execution.

    Attributes:
        quantity: Filled quantity in instrument units; always positive.
        price: Fill price in the quote currency, rounded to tick size.
        fee: Fee charged in `fee_currency`; debited exactly once.
    """
```

## Tests

Test names state the behavior they prove (`test_stale_quote_is_rejected`), so
test functions need no docstring. A test module keeps a one-line docstring.

## TypeScript and JavaScript

- JSDoc for exported functions, components, public classes and non-obvious
  types.
- Use `@param`, `@returns` and `@throws` only when they add meaning beyond the
  signature.

## Other files (SQL, YAML, TOML, shell, configuration)

Comment only the purpose, a constraint or the rationale near the line it
qualifies. Do not restate values the file already shows.

```yaml
# Crypto 4h bars close on UTC boundaries; equity bars follow the exchange calendar.
bar_close_timezone: UTC
```

## Inline comments

Explain **why**: an invariant, a constraint, a non-obvious trade-off or a side
effect. Never explain **what** the code already says.

| Good | Bad |
|---|---|
| `# Fill at next bar open: the signal used this bar's close.` | `# set price to next open` |
| `# Decimal from str avoids binary rounding of provider floats.` | `# convert to Decimal` |

## Prohibitions

Comments and docstrings must be self-contained. They must not contain:

- workflow or traceability IDs (`SPEC-…`, `REQ-…`, `PLAN-…`, `TASK-…`,
  `OD-…`), issue or pull-request numbers;
- agent attribution (`Co-Authored-By`, "generated by", "written by",
  "Claude Code", "Codex"); naming a model provider in an adapter is allowed;
- `TODO`, `FIXME` or `XXX` (open a backlog item instead);
- history notes ("previously", "old version", "temporary");
- banner or divider comments, numbered step narration, or commented-out code.

Traceability belongs in specs, `.work/`, commit messages and pull requests.
